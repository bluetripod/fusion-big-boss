# Fusion for Copilot CLI

Fusion supplies four agent profiles in [`agents/`](agents/) and a role-aware runtime guard in [`extensions/fusion-guard/`](extensions/fusion-guard/). The lead reads/analyzes source, codes, reviews and answers. Its persistent sidekick executes only precise coding changes, location-only file lookups and specified command/retrieval jobs. Optional read-only advisor/reviewer roles read source themselves and may use separate persistent evidence-only sidekicks. Review is user-requested only. The extension checks identity, ancestry and named-tool routes; task precision and source-preserving shell behavior remain instruction policies. See the [shared design](../README.md).

## Install and enable

Copilot CLI 1.0.89-5 rejects `copilot plugin install .`. Its supported local route is a **local marketplace** whose single plugin source points to this repository. Replace `/absolute/path/to/fusion` with the stable clone path; stop if any destination already exists rather than overwriting it:

```sh
mkdir -p "$HOME/.local/state/fusion-big-boss"
mkdir -m 700 "$HOME/.local/state/fusion-big-boss/copilot-marketplace-local"
ln -s /absolute/path/to/fusion "$HOME/.local/state/fusion-big-boss/copilot-marketplace-local/plugin"
(set -C; cat > "$HOME/.local/state/fusion-big-boss/copilot-marketplace-local/marketplace.json") <<'JSON'
{
  "name": "fusion-big-boss-local",
  "owner": { "name": "Local Fusion" },
  "plugins": [
    { "name": "fusion-big-boss", "source": "./plugin" }
  ]
}
JSON
copilot plugin marketplace add "$HOME/.local/state/fusion-big-boss/copilot-marketplace-local"
copilot plugin marketplace browse fusion-big-boss-local
copilot plugin install fusion-big-boss@fusion-big-boss-local
copilot plugin list
```

When upgrading from a differently named package, install `fusion-big-boss` and reapply your chosen models through `/fusion`; packaged role IDs now use the `fusion-big-boss:` prefix. Saved choices are read from the `fusion-big-boss/copilot-fusion.json` state path described below. To retain earlier recents, copy your previous history file there only if the destination does not already exist. The rename does not migrate installed settings or histories automatically.

This CLI reports local-marketplace plugins as **live**, not cached copies: source edits take effect in the next Copilot session. Preserve both the clone and marketplace paths. For migration, privately back up and retire only older loose `~/.copilot/agents/fusion*.agent.md` and `~/.copilot/extensions/fusion-guard/` once the installed package is verified; do not replace unrelated assets or settings.

In a new Copilot session, enable extensions with `/settings experimental on` if needed, then start another session. When prompted for `plugin:fusion-big-boss:fusion-guard` to **register hooks**, approve that capability for the location if you want persistent protection there; a different location may ask again. Do not use a blanket permission grant. Experimental mode alone does not approve hooks. Without the running guard, written agent instructions are not enforceable tool restrictions.

Use `/fusion` to configure the packaged lead and workers. Approve any additional command/tool-registration capability prompt explicitly; hook approval is still required for runtime protection. Old loose-profile selections need not transfer to the namespaced agents. The guard prevents direct lead/advisor/reviewer shell/search, restricts their text views to finite ranges of at most 350 lines, and permits lead-owned coding sidekick Git, native web search and known-URL fetch. Search guards recognize exact `web_search`, `github-mcp-server-web_search`, and `github-mcp-server/web_search` names present in the inspected 1.0.95 runtime; tool availability, arguments and approval remain native. Evidence sidekicks cannot use web tools. Only the lead can start consultations/reviews; each advisor/reviewer may start or control its own evidence-only sidekick, never borrow the coding worker. Sidekicks cannot delegate or control workers. Model configuration and ownership checks still apply, as do ordinary Copilot permissions.

Callers read and interpret decision-relevant source themselves, reusing sufficient current context. File-location jobs supply roots and concrete filenames/symbols/patterns and return locations only. Coding jobs require target files/symbols, exact changes, scope and specified checks; the lead may implement multi-file work directly. Delegate only when a fully specified handoff is worthwhile. Command/check failures or ambiguity return to the caller, not autonomous worker analysis or repair loops. Independent specified jobs may run concurrently where supported; coordinate conflicting writes and stable-tree checks. Steer a running worker within its existing task rather than launching a second concurrent job in that conversation.

The lead and each advisor may start multiple persistent sidekicks for independent tasks using fresh background `task` calls. Retain each returned `agent_id`; use `write_agent` for related follow-ups after that worker becomes **idle**. Workers share the user-selected sidekick model settings, with separate conversations and one active task per session. Advisor workers remain evidence-only and caller-owned; the reviewer must reuse its single evidence sidekick while it is running or idle. The 1.0.95 host rejects writes to terminal completed/failed/cancelled workers, so a terminal reviewer worker may be replaced with a new task and an explicit evidence handoff; its old output/history is retained.

Advisor consultations support native `mode: sync` as well as background. Sync callers retain verified role/ancestry and read-only evidence boundaries. Native `write_agent` only supports background workers; prefer background for live steering and same-consultation follow-ups. Synchronous advisors cannot be promised resumable conversations.

## Live worker controls

- **Status:** native `read_agent(agent_id, since_turn=...)` reads running state/history without a model turn. Inspect available progress; missing output is not proof of inactivity.
- **Message:** native `write_agent(agent_id, message)` can steer a running owned worker. Admission means queued, not read or obeyed. Request fresh progress or wrap-up with an ordinary message asking for findings, changed files, checks/results, blockers and unfinished work. There is no wrap-up action or automatic deadline.
- **Cancel:** extension tool `fusion_cancel(agent_id)` requests cooperative interruption of one owned worker and verified evidence descendants. Results distinguish `requested` (RPC attempted), `accepted` (host acknowledgement), and `confirmedStopped` (a subsequent terminal task status), with failures reported per worker. It returns available output (last 8,000 characters) and native progress (last 20 activity lines, up to 1,000 characters each), marking truncation or unavailable observations. It does not remove tasks, history, output or file changes. A final worker summary and instant cessation of writes are not guaranteed.

The lead controls direct sidekick/advisor/reviewer workers; advisors/reviewers control only their own evidence sidekicks. Messages and cancellation require one explicit ID and no model/effort/context overrides. Advisor ancestry is checked for reads as well as writes. Fresh tasks and writes observed as idle continuations validate the target's exact enabled `/subagents` configuration and available model/effort/context. Evidence callers also validate their own selected role and observed model before admitting new work. Running-worker steering, status and cancellation remain usable when model settings are disabled or unavailable; steering still requires Fusion on and no cancellation admission block. Native writes to idle workers start a continuation; terminal workers reject writes. Completion racing with a live write can become continuation, so there is no atomic running-only guarantee or atomic configuration check at delivery.

For related work that must wait, use native `read_agent(agent_id, wait: true)` (host-bounded timeout) or a completion notification, then `write_agent` after idle is observed. The SDK's `tasks.waitForPending` waits for the whole runtime, not one owned conversation; Fusion does not add a scheduler or replace native steering with a global wait.

Cancellation uses the installed 1.0.95 SDK's `joinSession({ tools })` registration and `session.rpc.tasks.cancel/getProgress/list`. Its handler verifies the attached root, SDK `agentId` and matching `tool.execution_start` caller evidence; missing or contradictory evidence fails closed. Before descendant discovery, the parent is blocked from admitting more evidence work. Accepted cancellation remains blocked until a successful native idle continuation is observed; rejected/failed cancellation is reported and releases the block. Tool-call/task identity and attachment-scoped cancellation generations prevent stale outcomes from reopening a later cancellation. Reattachment discards old in-flight authorization; native cancelled/terminal status still blocks new caller work. No additional cancellation state is written to user configuration.

Descendant cancellation uses a verified ancestry snapshot and reports untracked/unverified candidates; already-admitted children racing with the snapshot may remain unconfirmed. Task identity is checked again immediately before cancellation, and one post-request status observation is made without waiting for completion or polling. Offline tests exercise real SDK handler dispatch and RPC routing over an inert transport; live host cancellation settlement, tool availability/approval, steering delivery and completion notifications still require a CLI smoke test.

## Model setup and on/off

With interactive UI, `/fusion` opens a draft showing lead, sidekick, and optional advisor/reviewer choices. Each role offers its recent three model/effort/context choices or **Choose new model**. When text input is available, choosing a new model first asks you to **Search models**, for example `sol 6.1`: every whitespace-separated term must appear in the model's name or ID, case-insensitively and in any order. Submit the search, then select from the matching IDs; this is not live filtering inside the selection dialog. Exact duplicate IDs appear once; distinct IDs remain separate even if their names match. Blank input shows all models, no matches asks for another search, and cancelling the search keeps the draft unchanged. Hosts without text input retain the full-list picker. The current model is preselected when available; a search excluding it does not add it back. Effort and context are preselected only when editing the same model. Select an available model, its supported thinking effort, and its supported context tier where offered. Models without those options skip the corresponding step. Context choices display their total context capacity and maximum input token budget where reported or derivable from the host's tier input/output metadata; missing limits say **not reported**, never guessed. The selected values remain host-advertised `default`/`long_context` tiers, not arbitrary token lengths; long context may cost more. Advisor and reviewer also offer **None / disabled**. **Apply this setup** is the only action that changes models/settings; main-menu Cancel or Escape discards the draft. Escaping a role/model/effort/context submenu returns to the main menu without changing that role's draft choice. Opening the picker only prefills the last applied setup, never enables it automatically. Prefer a reviewer from a different model family than the lead (and author where practical); this is recommendation only, never detection, automatic selection, or enforcement.

Without interactive UI, use the same command with arguments:

```text
/fusion lead=<model-id>#<effort> sidekick=<model-id>#<effort> advisor=none
/fusion advisor=<model-id>#<effort>
/fusion reviewer=<model-id>#<effort> reviewer-context=long_context
/fusion reviewer=none
/fusion lead-context=long_context sidekick-context=default
/fusion status
/fusion off
/fusion apply
```

Use exact IDs from the model catalog (including a provider prefix when shown); omit `#<effort>` only for models without reasoning-effort options. The first setup requires lead and sidekick. Later text setup can update individual roles from the saved setup. `/fusion apply` explicitly enables the last saved setup. No model substitution or automatic model defaults are allowed.

Use `<role>-context=default|long_context` only for a tier supported by that role's model; combine it with a model choice or update a saved role. The summary and recents retain explicit context choices. Old saved choices without a context remain valid: the lead leaves context selection to native behavior, and worker writes preserve existing context overrides or leave the native default when none exists. Apply revalidates thinking/context support and confirms the lead's explicit tier after switching.

Apply selects this plugin's packaged Fusion lead, sets its model/effort, and writes worker selections with **Model enforcement: required** both to the current session and to native user settings, visible in `/subagents`. The `subagents` value is read and merged, preserving unrelated agents, disabled entries, and other options; other top-level user settings are untouched. Choosing advisor/reviewer none retains its existing configuration but disables it. Managed subagent settings or fail-closed policy block Apply. A managed `model` is an overridable startup default, not a ban on explicit session-model choices; native model availability and switch confirmation still apply. See GitHub's [managed model reference](https://docs.github.com/en/copilot/reference/enterprise-administrators/enterprise-managed-settings#model). Legacy `config.json` shadows reported by the host block success; every write must also read back the requested `subagents` value before live settings and history are applied. Native `/model` and `/subagents` remain available; manual changes do not update Fusion's private recents or saved setup.

Apply refuses while any Fusion worker task is running or its status cannot be verified. Off is allowed with background work: it selects the default agent and preserves the current lead model/effort, conversation, workers, native settings, and saved setup. Existing coding sidekicks retain their no-delegation boundary; advisors/reviewers and evidence workers retain read-only boundaries. Off blocks new advisor/reviewer evidence jobs, while owned status/cancellation remain available. Re-enabling requires explicit Apply; reopening the picker or asking for status does not enable Fusion.

The last applied setup and per-role recent three are saved atomically in `$XDG_STATE_HOME/fusion-big-boss/copilot-fusion.json`, or `~/.local/state/fusion-big-boss/copilot-fusion.json`, with file mode `0600`. Only explicitly selected roles enter recents after successful Apply. Old saved lead/sidekick/advisor model, effort, and context selections remain valid when reviewer fields/recents are absent; reviewer remains disabled until selected. Obsolete utility fields are ignored, never substituted into sidekick. Utility is no longer a recognized role or setup argument. Existing utility chats and native settings entries are left untouched and unused by Fusion. Missing/corrupt required-role history is treated as empty.

## Optional user-requested review

After selecting a reviewer, ask the lead normally: **“Do a code review with the Fusion reviewer.”** The lead uses it only for explicitly requested code review, never automatically after coding or fixing findings. It prepares the neutral, frozen packet defined in [User-requested code review](../skills/fusion-delegation/SKILL.md#user-requested-code-review), then invokes a fresh background `task` with `fusion-big-boss:fusion-reviewer`, or continues a confirmed retained same-change reviewer with `write_agent`. The lead chooses the conversation; you need not type task IDs. Unrelated work starts fresh. Missing-evidence follow-ups stay within the requested review; a separate review or re-review needs another ordinary user request. The lead retains planning, interpretation, fixes, and the final answer.

User intent is an instruction policy, not a runtime detector or authorization token. Under an active Fusion lead, the guard validates configuration for new/continued work, same-root start/parent evidence for retained reviewers, and supported worker status. Reviewer writes require one explicit `agent_id` with no model/effort/context overrides; task-registry IDs are not runtime child-session IDs. When Fusion is off, ordinary root task/message behavior remains native except messages targeting retained Fusion workers (including group messages that would reach them). Existing Fusion descendants retain their role boundaries regardless of the selected root agent.

Reviewer tools are bounded text `view` (explicit finite 1–350-line inclusive ranges), native `skill`, and `task`/`write_agent`/`read_agent`/`fusion_cancel` solely for its own evidence sidekick. Advisor has the same reads/evidence delegation, without review-skill loading. Evidence sidekicks expose file-location and shell-session tools only; commands must be read-only Git inspection or specified checks, preserving source and the frozen snapshot. Requested log/test artifacts are allowed, but no edits, staging, commits, pushes, repairs, web or nested delegation. An unverified role/ancestry fails closed. Shell scripts are not sandboxed by named-tool guards.

Load installed `code-review-and-quality` with native `skill`; relevant specialized guidance is optional. Fusion does not install/fetch/vendor skills. If `skill` is unavailable, read an advertised SKILL.md in bounded ranges; otherwise disclose the limitation and use the inline contract. Distinguish supplied test results from requested evidence-sidekick checks. Offline tests do not establish live skill availability, nested native delivery, host approval, completion notification or existing-child model changes.

Host RPC changes are not transactional: a later failure may leave an agent/model or persisted settings changed, but does not record successful setup/recents. A deferred model switch may still run later; wait for the session to settle and inspect native settings before retrying. Avoid simultaneous `/subagents` edits in another session during Apply; merging preserves the values read, not edits made concurrently after that read. Command approval and live picker/switch behavior still need verification in the running CLI.

SDK compatibility: the session catalog is `session.rpc.model.list`, not the server's `models.list`. Native `user.settings.get/set` are server-scoped and absent from the session RPC surface returned by `joinSession`. `settings.mjs` sends those same RPCs through the session's existing `connection.sendRequest` transport, an SDK-private property; it opens no additional connection and fails closed if the transport is unavailable. Offline actual-session/native-helper checks pass against locally available bundles 1.0.90-1/-2/-5/-6/-7; this does not establish live host approval or effective-settings behavior on every version.

The inspected 1.0.93 SDK declares `user.settings.set` as returning no value (`null`/`undefined` over the transport); 1.0.93-1 declares a `shadowedKeys` result. Apply accepts both contracts, retains explicit shadow rejection when available, and confirms the full merged `subagents` value through `user.settings.get`. Mismatched, missing, or unreadable read-back does not update live settings or saved setup/recents, even if the persisted write landed. Read-back confirms only the values exposed by that host: 1.0.93 describes settings.json values, while 1.0.93-1 also describes legacy config.json overlays; neither includes repository or enterprise overrides.

Native CAPI session entries expose thinking levels in `capabilities.supports.reasoning_effort` and tiered prices in `billing.token_prices.default/long_context`; normalized relay entries can expose `supportedReasoningEfforts` and `supportedContextTiers`. Fusion reads both proven representations without manufacturing model-specific levels or token budgets. Packaged agent identity compares real filesystem paths, so local-marketplace symlinks work without accepting a foreign plugin's profile. Missing or ambiguous agent identity still blocks Apply and reports only IDs/names/source/path presence for diagnosis.

## Checks and limits

From the **repository root**, run `npm ci --ignore-scripts` to install development dependencies, then `npm test` for the guard, entrypoint, packaging, and briefing checks. After editing the shared [`skills/fusion-delegation/SKILL.md`](../skills/fusion-delegation/SKILL.md), run `npm run sync:briefing` before checking: it refreshes marked sections of the lead, sidekick, and reviewer profiles. `node scripts/generate-briefing.mjs --check` checks those copies without writing them. Edit host-specific instructions outside the generated markers. `npm run check` runs the full local workspace checks, including other adapters.

The optional installed-SDK contract test constructs a real `CopilotSession` with an inert transport, without CLI startup or inference. It also uses the bundle's native helpers for isolated, unauthenticated local-plugin discovery through a temporary symlink and for capability-fixture validation. It defaults to `~/.copilot/pkg/linux-x64/1.0.90-5/copilot-sdk/index.js`; set `FUSION_COPILOT_SDK` to another CLI bundle's `index.js` (with its sibling native runtime) to check that bundle. If the default SDK is absent, that optional test skips; an explicitly selected missing SDK fails.

The guard checks named tools and verified roles, not arbitrary side effects of shell scripts or network programs. Tests do not prove that an already-running Copilot session has loaded the latest source. Model, authentication, and permission choices remain under your control.
